## P1 — Must Fix Before Release

### AUD-P1-01 · Marketplace-bid counteroffer is a dead end — the worker cannot see or answer it, and both sides misrender the state
- **Files:** `screens/JobDetailScreen.tsx:499-534`, `lib/offers.ts:277-287`, `screens/BidDetailScreen.tsx:254-271,315-329`, `screens/MessagesInboxScreen.tsx:73-79`, `supabase/phase46_offer_rpcs_and_rls.sql:263-273`, `supabase/phase50_sandbox_payments_and_offer_lifecycle.sql:863-869`
- **Path:** Worker bids on an open job → customer opens BidDetail → taps **Counter** (screen 30, shipped in Phase 5) → `counter_offer` succeeds, new pending row has `author_id=customer`, `awaiting_id=worker`. From that moment no screen lets the worker respond.
- **Evidence:** Marketplace chains never get chat negotiation cards: `create_offer` posts a root message only for `direct_offer` (phase50:863-869) and `offer_post_event` early-returns without one (phase46:263-266) — so ChatScreen's Accept/Decline/Counter cards never exist for bids. `my_pending_offers` returns NULL thread keys for bids, so the inbox badge keys as `direct:null` and never matches. No notification trigger covers counters. The worker's JobDetail renders the customer's counter as **"Your bid"** with the customer's amount (`fetchMyOfferForJob` filters only `worker_id + status='pending'`; JobDetailScreen has no `author_id`/`awaiting_id` check — verified by hand), and its only action, **Withdraw**, fails server-side because `withdraw_offer` is author-only. The customer waits on "You countered — waiting for {worker} to respond" for 7 days until expiry.
- **Impact:** Every marketplace-bid negotiation that uses the first-class Counter action deadlocks: the worker never learns it happened, sees wrong money labeled as their own bid, and their one offered action errors. The Phase-5 two-device checklist that would have caught this (steps 10–12) is still marked PENDING.
- **Fix:** Make the worker's own-bid card negotiation-aware: when `pending.author_id !== viewer`, render "Customer countered $X" with Accept/Decline/Counter wired to the existing `acceptOffer`/`declineOffer`/`counterOffer`, and enqueue a counter notification.
- **Confidence:** HIGH — found independently by two agents, 4/4 verification verdicts CONFIRMED P1.

### AUD-P1-02 · Unfundable-race dead end: once an unfunded job leaves `assigned` there is no checkout path — the worker can never be paid
- **Files:** `screens/ClientJobDetailScreen.tsx:772,798-803,898-955`, `screens/ChatScreen.tsx:345-350`, `screens/ApproveOrDisputeScreen.tsx:259-266`, `supabase/phase58_hardening_fixes.sql:66-131`
- **Path:** Customer accepts a bid and backs out of Checkout without tapping "Authorize & protect" (checkout never auto-authorizes), **or** accepts a direct offer in Chat (whose success path is only an alert and never prompts checkout). Worker taps Start (allowed with no payment precondition by deliberate phase51 design), then Complete.
- **Evidence:** `ClientJobDetailScreen.tsx:772` forks the checkout CTA on `status === 'assigned'`; at `in_progress` the else-branch renders `payment ? <Card/> : null` — no payment section, no checkout route. At `completed`, "Finish checkout" (942-954) is nested inside `payment ? (...)`, so a null ledger falls to the legacy inline review. `ApproveOrDispute` renders "NO PAYMENT ON THIS JOB … nothing to release". Repo-wide, all five navigations to `'Checkout'` are unreachable in this state. phase58's server-side authorize-after-start fix exists precisely for this race but no UI can invoke it.
- **Impact:** A realistic path (especially direct offers) runs a job to `completed` with an empty ledger; screens present it as a settled legacy job, the worker is never paid, no tip is possible, and checkout is never offered again.
- **Fix:** Render the checkout CTA whenever the viewer owns the job, status ∈ {assigned, in_progress, completed}, and the payment row is null/authorized; have Chat's direct-offer accept route into Checkout.
- **Confidence:** HIGH — 2/2 verification verdicts CONFIRMED P1.

### AUD-P1-03 · `.env` bakes the STAGING project into every locally-built binary and OTA update; the production pair is still commented out "RUN-DISABLED"
- **Files:** `.env:3,5,8-9` (hosts only inspected), `lib/supabase.ts:4-11`, `babel.config.js:5-17`, `package.json:54-55`, `DECISIONS.md:484-527`
- **Path:** Cut any build or publish any OTA from this tree today (`npm run release:testflight` locally, `npm run update:preview`, `expo export`) → `react-native-dotenv` inlines `.env` at Babel transform time → the shipped bundle talks to staging `zzkumxcjtbqoselzptig` (seeded fixtures, `@brazos.test` identities), not production `avkighsiufeefyycbebf` — which had phase51-58 applied on 2026-08-11 for exactly this release.
- **Evidence:** `.env` active pair = staging under the "AUTONOMOUS RUN (phases 6-12)" header; production URL/key commented out as "RUN-DISABLED production value — restore after the autonomous run" — the run is over and the restore has not happened. `babel.config.js` uses `api.cache(true)`, so even after restoring, a stale Metro cache can bake old values (DECISIONS.md documents this exact class biting once in reverse). The OTA aggravator: `update:preview` publishes a locally-baked bundle to the same `preview` channel every distributed binary subscribes to (`eas.json`, `app.json` fingerprint runtimeVersion) — one habitual publish after a release can silently flip installed apps' backend.
- **Impact:** "Production configuration pointing at a wrong environment": real users on the staging DB, or all sessions invalidated by an OTA backend flip.
- **Fix:** Restore the production pair as the active `.env` values, clear the Metro/babel cache, and add a release-gate assertion that the baked ref equals `avkighsiufeefyycbebf` (`scripts/verify-schema.mjs` already has ref-parity machinery).
- **Confidence:** HIGH — 6/8 verdicts P1 across four independent discoveries (two P2 votes argued "documented deliberate cutover"; the restore window has passed, so the hazard stands).

### AUD-P1-04 · The release pipeline does not determine the production backend; an EAS cloud build's backend depends on invisible dashboard state, with a crash-on-launch failure mode
- **Files:** `eas.json:1-16`, `babel.config.js:12-15`, `lib/supabase.ts:6-11`, `.gitignore:44`, `package.json:54`

- **Evidence:** `eas.json` defines ONLY `testflight` (channel `preview`, environment `preview`) — there is **no production profile**. If the EAS "preview" environment doesn't define `SUPABASE_URL`/`SUPABASE_KEY`, the build is green (`allowUndefined: true`, comment defers failure to runtime) and the binary throws at module scope on every launch ("Missing Supabase configuration") — `--auto-submit` pushes it to TestFlight anyway. - **Impact:** The single defined release command ships either an instant-crash binary or a backend chosen by invisible state.
- **Fix:** Add a `production` EAS profile with `SUPABASE_URL`/`SUPABASE_KEY` pinned to `avkighsiufeefyycbebf` in a production EAS environment, plus a pre-build check that fails when they're absent.
- **Confidence:** HIGH on mechanism (verified to the plugin source); the dashboard state itself is Unverified item #1. Both verifiers: ADJUSTED to P1 (P0 requires a demonstrable branch).

### AUD-P1-07 · Post-job draft — including the exact private service address and media — is device-global and survives logout; the next account inherits it
- **Files:** `lib/postJobDraft.ts:16,27-28`, `lib/AuthContext.tsx:124-132`, `screens/MyJobsHubScreen.tsx:104-110`
- **Path:** User A drafts a job (title, **exact address**, photos), kills the app (autosave by design), logs out. User B signs in on the same device → My Jobs shows A's "resume draft" card; B can open, read the address, and publish A's half-written job as their own.
- **Evidence:** `DRAFT_STORAGE_KEY = 'brazos:postJobDraft:v1'` — a single device-global key, unlike the neighboring per-user `setupStorageKey(userId)` / `modeStorageKey(userId)` stores (whose per-user isolation is even test-asserted). `logout()` clears only the push token. Draft shape includes `address` ("Exact service address (private — job_private_details on publish)") — the very field the architecture confines to owner + hired worker via RLS. Verified by hand.
- **Impact:** Cross-account residue of exactly the data class the DB layer exists to protect.
- **Fix:** Key the draft by userId (mirroring `setupStorageKey`) or clear `DRAFT_STORAGE_KEY` in `logout()`.
- **Confidence:** HIGH — 2/2 CONFIRMED P1.

### AUD-P1-09 · Cross-tab landings on an unvisited tab orphan that tab's root for the whole session (e.g. Messages inbox unreachable after a notification cold start)
- **Files:** `lib/navigationRef.ts:124-128`, `lib/notificationRoutes.ts:104-105`, `screens/NotificationsScreen.tsx:77`, `screens/ChatScreen.tsx:385-390`
- **Path:** Kill app → tap a chat push → replay parks and flushes at onReady → `navigateAcrossTabs('Messages','Chat',{jobId})` mounts the never-visited Messages stack with Chat as its ONLY route. The tab bar button thereafter pops-to-top onto Chat; no in-app dispatch targets `MessagesInbox`, so the inbox list is unreachable until app kill or a double mode-switch.
- **Evidence:** The nested navigate carries no `initial: false`, so React Navigation uses the target as the stack's initial route. The repo's own 2026-08-11 record confirms the mechanism on device ("Root-of-stack is therefore a NORMAL state in this app") — the `goBackOrHome()` fix removed the GO_BACK crash but not the orphaning: back now escapes to Home, and the tab still has no root beneath its landing screen. Same class affects MyJobs (Chat's cross-tab jumps land `ClientJobDetail`/`WorkerJob` as roots).
- **Impact:** After the routine act of opening the app from a message notification, a whole tab is reduced to one conversation for the session.
- **Fix:** Include `initial: false` in the nested payload of `navigateAcrossTabs()` (or pre-dispatch the tab root) so the declared root always sits beneath a cross-tab landing.
- **Confidence:** HIGH on mechanism (2/2 CONFIRMED P1); exact runtime behavior in both trees is device-matrix item 5.

### AUD-P1-10 · Android builds have no Google Maps API key — the Map tab on a compiled Android build crashes or renders permanently blank
- **Files:** `app.json:20-33,39-66`, `components/HotspotMap.native.tsx:4,129`, `package.json:30`
- **Path:** Any real Android build (dev-client/EAS — not Expo Go) → Map tab → grant location or "View map without location" → `MapView` mounts.
- **Evidence:** `react-native-maps 1.20.1` renders `MapView` unconditionally; `app.json` has no `android.config.googleMaps.apiKey` and no maps plugin; managed workflow means prebuild emits an AndroidManifest without `com.google.android.geo.API_KEY`. The Google Maps SDK without that meta-data throws at map init (or renders a blank tile grid). Expo Go masks it (ships its own key) — every recorded device pass has been iOS/Expo Go.
- **Impact:** One of the five main tabs broken (possibly fatally) on the entire Android platform.
- **Fix:** Add `android.config.googleMaps.apiKey` (via EAS secret) before any Android build; verify the Map tab on an Android device.
- **Confidence:** MEDIUM-HIGH (repo side proven; crash-vs-blank is runtime-dependent — device-matrix item 3). Verdicts: CONFIRMED P1 / ADJUSTED P2; held at P1 since Android device testing is in scope for release.

### AUD-P1-11 · iOS "Save Image" from the share sheet kills the app: `NSPhotoLibraryAddUsageDescription` is missing while the share flow is built to surface it
- **Files:** `app.json:16-18`, `lib/sharing.ts:8-13,75-90`, `components/PhotoViewer.tsx:69-75`

- **Confidence:** HIGH — 4/4 verdicts CONFIRMED P1 (across the two agents that found it).
