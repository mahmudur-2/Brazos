### 1.3 Edge functions and their contracts

**House style** [VERIFIED, every function's header]: plain `fetch` to PostgREST — no
`supabase-js`, no import map, no `_shared/` — every function dependency-free. The single
amendment: `stripe-webhook/index.ts` imports its sibling `./verify.mjs` by relative path,
because that file is plain JavaScript with no imports and is executed by
`tests/stripeWebhookSignature.test.mjs` inside `npm run verify` (ten cases). **No edge
function computes a monetary amount** — every cent sent to the provider is read verbatim
from a `payments` column. Nothing under `supabase/functions/` is typechecked
(`tsconfig.json` excludes it) and no Deno handler is executed by any test here.

`supabase/config.toml` `[functions]` entries [VERIFIED, the file]:
`[functions.stripe-webhook] verify_jwt = false` (the provider sends no JWT; the signature
check is the endpoint's authentication and the database grants are its defence);
`[functions.create-payment] verify_jwt = true` (written out although it is the default);
no other entry — `send-push`, `worker-search`, `translate` and `process-settlements` run
over the platform default, the last woken by pg_cron with the service-role key as Bearer.
**After every deploy, confirm the dashboard's per-function toggle for `stripe-webhook`
still shows JWT verification OFF** — the dashboard can override the file and a CLI
redeploy can reset the dashboard.

#### 1.3.1 The webhook response rule — VERIFIED HANDOFF.md R5

| Condition | Response |
|---|---|
| signature invalid, missing, or the check threw | 400 `{"error":"invalid signature"}`, no side effects, no detail |
| event type outside the seven | 200 `{"ok":true,"ignored":<type>}`, NOT recorded |
| `payment_events` insert returns 409 / 23505 | already STORED, not already applied — falls through and applies |
| the insert fails any other way | 500 |
| `apply_payment_event` returns `ok:true` | 200 |
| `ok:false` and `attempts >= 5` | 200 — the row stays recorded with `processed_at` null (first signal query) |
| `ok:false` and `attempts < 5`, or the row cannot be read | 500, so the provider retries |
| the RPC is unreachable, or anything throws | 500 |

An event that resolves to NO ledger row (a dashboard-sent synthetic intent; a transfer
without metadata) is `ok:true` with a null `payment_id` and a SET `processed_at` — it never
appears under `processed_at is null`; the second signal query (§1.7) is what finds it.

#### 1.3.2 `create-payment` — the contract R6 codes against — VERIFIED HANDOFF.md R5

- Request: `POST` with a Supabase user token; body `{"jobId":"<uuid>"}` (`job_id` accepted).
- `begin_job_payment()` runs AS THE CALLER (the Authorization header forwarded with the
  anon `apikey`); `get_payment_customer` / `set_payment_customer` and `attach_provider_ref`
  run as service_role. The function needs no table access.
- Provider calls and idempotency keys: `POST /v1/customers` `brazos-customer-<user id>` (a
  double-tap guard only — durable reuse is the stored reference); `POST /v1/ephemeral_keys`
  — no key, deliberately, and the ONLY call carrying a version header,
  `Stripe-Version: 2026-08-26.dahlia`; `POST /v1/payment_intents` `brazos-intent-<payment id>`
  with `amount` = `charge_amount_cents` verbatim, `currency=usd`, `customer`,
  `metadata[payment_id]` and nothing else — **no `automatic_payment_methods`**. No `/v2/`
  path anywhere in the repository.
- Response 200: `{"paymentId","customerId","clientSecret","ephemeralKeySecret"}` — four
  strings, **no amount**: the client displays `charge_amount_cents` from the `payments` row.
- Failures: 4xx `{"error":"<the message begin_job_payment raised>"}` verbatim ("Payments
  are paused right now. Please try again shortly.", "Accept an offer before protecting a
  payment", "Job not found"); 401 no session; 409 the row has no amount yet; 502 the
  provider is down.
- **The ephemeral-key version line.** The mobile SDK may require ITS OWN version string on
  `/v1/ephemeral_keys`; if the payment sheet rejects the key, that one header is the fix.
- `payments.status` is what the UI reads: `unfunded` until `payment_intent.succeeded`
  lands; the client re-reads the row and never claims "held in protection" off a
  successful sheet.

### 1.4 The staging pipeline — supersedes v2 §4.4 and ADR-0010

v2 §4.4 documented a hand-triggered migration workflow and recorded `workflow_dispatch`
as the standing decision (ADR-0010). **Both are overtaken**: A0 built that workflow
(`59e4738`), A1 deleted it and replaced it with one pipeline (`3a8e6a8`), and A1-FIX /
A1-WIRE (`9f60a3e`, `edd7a89`) made its pending-set parse survive the pinned CLI's table
format. This section describes `.github/workflows/staging.yml` and
`scripts/staging-scan.sh` as they are. [VERIFIED both files; git log]

**Triggers.** `push` to `mainexpo` touching `supabase/migrations/**`,
`supabase/functions/**` or `supabase/config.toml` (the last so a `verify_jwt` edit can
never sit undeployed); `workflow_dispatch` with one boolean input `allow_destructive`
(default false). `permissions: contents: read`. Concurrency group `staging-pipeline` with
`cancel-in-progress: false`: a newer push cancels a superseded PENDING run, never one
mid-apply, and because every run applies everything pending and deploys everything, the
newest run finishes the older runs' work.

**Three jobs, strictly ordered, all unconditional** — no path filter, no changed-files
logic, no `if` beyond the `needs` chain:

1. `verify` (ubuntu, 15 min): checkout and setup-node pinned to full commit SHAs, Node from
   `.nvmrc`, `npm ci`, `npm run verify`. A deliberate duplicate of `ci.yml` — chaining by
   `workflow_run` fails OPEN, and a money pipeline re-runs the suite itself.
2. `migrate` (`needs: verify`; environment `staging`, restricted to `mainexpo`, holding
   `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD` — the ref appears
   only as a secret reference; 10 min). The CLI is `npx --yes supabase@2.116.0`, the version
   the operator runs locally; no third-party action ever holds these credentials. Steps:
   link the project → `migration list` (BEFORE) → **the safety gate** → `db push` →
   `migration list` (AFTER). The two listings are the job's evidence.
3. `deploy` (`needs: migrate`; environment `staging`; 10 min): `functions deploy` for EVERY
   function, then `functions list`. `verify_jwt` is never passed as a flag —
   `config.toml` is its only source. A destructive-flagged migration therefore also blocks
   that push's function deploy, correctly; the override re-run performs both, in order.

**The safety gate** is two calls into `scripts/staging-scan.sh`:

- `migration list | bash scripts/staging-scan.sh --pending-files -` — the pending set comes
  from the DATABASE, never the git diff. Contract: stdout is one resolved migration path per
  line and nothing else; every diagnostic, including the raw table, goes to stderr; exit 0 =
  resolved (legitimately empty); exit 1 = FATAL (an unreadable table, or a pending version
  matching no file — reading zero versions while migration files exist is FATAL); exit 2 =
  misuse. Normalisation, not special-casing: U+2502 becomes an ASCII pipe, every backtick is
  removed, per-cell whitespace stripped; a row is PENDING when its LOCAL cell holds a
  14-digit version and its REMOTE cell is empty. The workflow captures the status with
  command substitution and `|| status=$?`, because `mapfile` fed by a process substitution
  reports the builtin's success and would turn a FATAL into an empty pending set the apply
  step reads as "nothing pending".
- `bash scripts/staging-scan.sh "$ALLOW_DESTRUCTIVE" <files…>` — `ALLOW_DESTRUCTIVE` is
  `true` only when the dispatch input was checked, else `false`; anything but those two
  literals exits 2; zero files is success. Comments and function bodies are stripped first,
  then seven case-insensitive, whitespace-tolerant patterns: `drop table`, `drop column`,
  `drop schema`, `truncate` **anchored to statement position** (start of line or after `;`
  — TRUNCATE is also a privilege name the baseline grants eleven times), `rename to`,
  `rename column`, `delete from`. (The script's prose still says "six"; the array holds
  seven.) `drop policy / trigger / index / constraint` deliberately do not fire — they are
  this repository's idempotent idiom. Exit 1 when flagged with `false`, before anything is
  applied; exit 0 when flagged with `true`, every hit still printed — a silent bypass is a
  blind spot. It is a tripwire for the trivially detectable class, not a proof of
  compatibility; the local suite that had to be green before commit is the real protection.

**Why "safe" means this** [VERIFIED `staging.yml` header]: staging is what the installed
TestFlight builds read; production has no users. Additive SQL cannot break an installed
build; removing or renaming what a build still reads breaks it the moment it lands.
Production is never automated and no job in this repository targets it.

**A migration adding an enum value must be its own file** — each file is one transaction
and Postgres will not let a new label be USED in the transaction that ADDED it.
[VERIFIED `staging.yml` header]

`ci.yml` [VERIFIED]: `push` and `pull_request` on `mainexpo`, plus `workflow_dispatch`;
one job, `npm run verify`; no database, no secrets, no deploy. pgTAP runs locally only
(`npm run db:test`); v2 §2.7's CI-side stack start / pgTAP / generated-types drift check

### 1.7 The money-path test plan, reconciled to the pipeline

HANDOFF.md's R5 test plan predates A1: its step 1 names a "Migrate staging" workflow that
no longer exists, and steps 4–5 hand-deploy the three functions in order. The pipeline
performs all three. The reconciled sequence:

1. **Run the pipeline once** — Actions → *Staging pipeline* → Run workflow on `mainexpo`,
   `allow_destructive` unchecked (or let R5b's push trigger it). Read the migrate job's
   BEFORE / AFTER listings: `20260910000000_settlement_schedules.sql` moves from pending to
   applied. The deploy job then deploys every function, after the migration. This first
   run is also the only live proof of the pending-set parse — watch it, do not merely start it.
2. Confirm the timers: `select jobname, schedule from cron.job order by jobname;` — expect
   `auto-release-due-payments`, `brazos-drain-push`, `brazos-process-settlements`,
   `expire-unfunded-payments`. Only `brazos-drain-push` present means the migration did not
   apply — stop.
3. Confirm `STRIPE_WEBHOOK_SECRET` and `STRIPE_SECRET_KEY` are listed on the edge-function
   settings page (both were already there; set nothing).
4. Confirm `stripe-webhook`'s per-function toggle shows JWT verification **OFF**.
5. Send one synthetic `payment_intent.succeeded` from the provider dashboard: delivery
   shows 200, and the second signal query returns one row with a null `payment_id`. That is
   correct, not a failure — it proves reachability, signature and recording; it cannot
   prove a ledger move because there is no row to move.
6. A real flow in the app (R6 is the prerequisite), watching the `payments` row:
   `provider_ref` set and `status = unfunded` after checkout starts, `funding_due_at` ~24h
   out; `held` with `held_at` after the card is paid (still `unfunded` means the webhook is
   not arriving — check delivery attempts); on release `release_requested_at` and
   `transfer_cents` set while `status` stays `held`, then within five minutes the drain
   runs and `transfer.created` sets `released` + `transfer_ref` — **the worker must have a
   connected payout account (R5b) or the row waits in the queue under `blocked`**; on a
   cancellation `refund_cents` / `refund_reason` set, the drain refunds, `charge.refunded`
   sets `refund_ref` and `refunded` / `partially_refunded`.
7. Read the drain's summary in the function logs every five minutes; `defects` is never
   expected to be non-zero.
